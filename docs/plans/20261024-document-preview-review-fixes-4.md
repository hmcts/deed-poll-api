# Plan: close the remaining JPEG-in-TIFF fallback

## Overview

A focused Copilot review of the TIFF structure check (`docs/plans/completed/20261023-document-preview-review-fixes-3.md`;
workspace `local-notes/deed-poll-api/api-preview-direct-review-4.jsonl`) found one **MEDIUM** defect and otherwise no
issues:

- A TIFF marked uncompressed (`Compression` 1) can still carry `JPEGInterchangeFormat` (513) and
  `JPEGInterchangeFormatLength` (514). If it also omits `ImageWidth`, `ImageLength` or `SamplesPerPixel`, the JDK's
  `TIFFImageReader.initializeFromMetadata()` invokes its JPEG reader to recover them. That fallback ignores the
  declared length, so a one-byte declaration does not bound its header and ICC reads, and several disjoint IFDs can
  point at the same JPEG bytes, repeating the parse outside `TiffStructure`'s byte accounting.

**Decision (Steve's 2026-10-23 decision 2, extended):** JPEG data in a TIFF is not previewed, whatever the declared
compression. So:
1. Refuse any IFD that carries a JPEG-related tag: `JPEGTables` (347) and the old-style JPEG tags 512 to 521
   (`JPEGProc`, `JPEGInterchangeFormat`, `JPEGInterchangeFormatLength`, `JPEGRestartInterval`, `JPEGLosslessPredictors`,
   `JPEGPointTransforms`, `JPEGQTables`, `JPEGDCTables`, `JPEGACTables`), regardless of `Compression`.
2. Require `ImageWidth` (256), `ImageLength` (257) and `SamplesPerPixel` (277) present in every IFD, so the reader has
   no reason to recover dimensions from elsewhere. Check whether the JDK reader also falls back for any other missing
   tag (for example `BitsPerSample`, `PhotometricInterpretation`, `RowsPerStrip`, strip/tile offsets) and require or
   refuse those too if it does, recording what was checked in the JDK source (read-only; do not run `javap`).

Both answer the fixed `PREVIEW_INVALID_DOCUMENT`. Leave the disjoint-payload rule as it is: no writer is known to need
shared payloads, and a narrow allowance can come later if real files are refused.

## Execution notes

**Execution baseline:** `c66b72c744ec3f33f1f87bd254ede363a39e0753` (this branch's HEAD when the run started).

**Task 1.**
- JDK source read (JDK 21's `src.zip`, read-only): `TIFFImageReader.initializeFromMetadata` falls back to the stream
  only once: when ImageWidth, ImageLength or SamplesPerPixel is missing and JPEGInterchangeFormat is present, it runs
  the JPEG reader at that offset, also taking the default BitsPerSample from it. Every other missing tag gets a
  constant: Compression (none), PhotometricInterpretation (derived from compression, ColorMap or sample count),
  SampleFormat, BitsPerSample, ExtraSamples, RowsPerStrip (whole height), TileWidth/TileLength, PlanarConfiguration
  (chunky). Missing strip/tile offsets throw (`getTileOrStripOffset`). Missing byte counts are estimated
  (`getTileOrStripByteCount`, `TIFFIFD.calculateByteCounts`), but `TiffStructure` already refuses offsets without
  counts. So the only new requirements are the three dimension tags, in every frame directory (depth 0; EXIF, GPS and
  Interoperability directories carry none).
- `TiffStructure` refuses JPEGTables (347) and tags 512 to 521 in any directory as "TIFF JPEG tag", once each
  entry's bounds and byte counts are checked, so the committed aliasing probe (JPEGTables entries) is still refused
  for covering more than the file. A frame without 256, 257 or 277 is "TIFF frame without its dimensions". Both
  reach the renderer as `PREVIEW_INVALID_DOCUMENT`.
- Tests: `TiffStructureTest.jpegTags` (each of the 11 tags alone, in a frame, in an EXIF directory and in the second
