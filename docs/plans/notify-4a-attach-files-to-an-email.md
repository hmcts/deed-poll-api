# notify-4a — attach files to an email

## Overview

The first half of the old `notify-4-forms-for-completion.md`, split on 2026-09-25. **Rewritten 2026-09-26** after
[`notify-4b`](completed/notify-4b-generate-the-deed.md) merged (api #52), because two things made most of the
original plan unnecessary:

1. **The five static forms are attached to the template in GOV.UK Notify.** Steve found this on 2026-09-25 while
   authoring ① in the portal. LOC021, LOC023, LOC024, LOC027 and LOC028 are the same bytes for every applicant, so
   Notify holds them and **api never touches them**. The only document api supplies is the generated deed, through
   the single `deed_document` key. The original Task 3, *store the five forms in api*, is therefore **withdrawn,
   not deferred**. Do not build storage for them.
2. **notify-4b built the rest.** It needed the drain-time upload seam (this plan's Task 1) and the per-type
   routing (this plan's Task 2) to send anything, and was told not to wait. Both are recorded below as done.

**What is left is proof and wiring, not code:** read the authored templates back from Notify, send ① for real
from a local api, and record exactly what stops ① and ② sending in AAT. **Tasks 3 and 4 need a person**: a
Notify template id only the portal shows, and a guest-listed inbox someone has to open. Do not run this plan
unattended.

## Which email carries which forms

| | ① adult | ② minor | ③′ relinquishment |
|---|---|---|---|
| Sent for `DeedPollType` | `Adult`, `AdultTransgender` | `Minor`, `MinorTransgender` | `DeedOfRelinquishment`: **not declared**, see decision 4 |
| Deed, **generated by api** (`((deed_document))`) | LOC020 | LOC022 | unknown |
| **Attached to the template in Notify** | LOC021, LOC027 | LOC023, LOC024, LOC028 | unknown |
| The email says | *"three forms"* | *"four forms"* | — |
| Authored in Notify (non-prod) | **yes**, 2026-09-25 | **not yet** | — |

`Unknown` is offered nothing: sending the wrong deed means swearing the wrong legal instrument, so it has no safe
default. The content draft, now matching this table, is
[`deed-poll-admin/.business_context/notify-templates/forms-for-completion.md`](../../../deed-poll-admin/.business_context/notify-templates/forms-for-completion.md).

**Notify is where a wrong attachment gets through, and api cannot catch it.** api decides only which *template*
a case gets. The files attached to each template are portal configuration, so LOC023 attached to ① would reach
every adult applicant with nothing failing. The only checks are the table above, which Task 3 compares against
what Notify publishes, and whoever replaces an attachment.

## Decisions taken — implement these, do not revisit

1. **~~The five blank forms are stored files in api.~~ Superseded 2026-09-26: Notify holds them** (overview,
   point 1). api has no key, no row and no blob for any of them.
2. **The personalisation stores a document *reference*, and the drain resolves it to an upload.** The resolved
   map is never written back. *(Implemented by notify-4b: `DocumentUploads`.)*
3. **`confirm_email_before_download` is `true`**, a missing or unreadable document is `TEMPORARY`, an
   unresolvable key or a document over 2 MB is `TECHNICAL`, and neither is ever `PERMANENT`. *(Implemented, with
   the amendment recorded in Task 1.)*
4. **Deed of relinquishment stays refused, and ③′ is not declared. Steve, 2026-09-26.** The journey is settled
   (the same as a change of name), but which forms it carries is not. notify-4b already refuses a relinquishment
   in its own words, which tells a caseworker what is actually missing. Declaring an unprovisioned ③′ would say
   only "not set up in Notify", as if a template id were the gap. Declare it when someone identifies the forms
   (flag 3).
5. **The deed link's retention is 26 weeks. Steve, 2026-09-26.** That allows time to print, find two witnesses
   and a commissioner of oaths, and absorb delays. Inside the 1–78 weeks `NotifyProperties.retention` accepts.
6. **The email says "download", not "attached".** A Notify file is a link, not a MIME attachment.
7. **The ① and ② template ids do not go into the chart yet.** Setting a template id makes the email offered in
   AAT at once (`isProvisioned` never looks at the API key; see `values.yaml`), and AAT has no Notify key. For
   ③ and ⑤ that means a visible failure. For ① it costs the case its forms email for good: the send generates and
   stores the deed, the drain fails `TECHNICAL: Empty key`, and the dead row still holds V20's slot, so every
   re-send answers with it. **Both chart settings wait for flags 1 and 2.** Tasks 3 and 4 use environment
   variables in a local api only.

## Tasks

### Task 1: Resolve a stored document to a Notify upload at drain time

Read first: `NotifyEmailSender.send`, `NotificationOutbox`, and decisions 3, 4, 5, 7 and 8.

- Immediately before `sendEmail`, replace each document id in the personalisation with
  `NotificationClient.prepareUpload(bytes, filename, true, retention)` — `true` being decision 4, the retention
  from configuration per decision 5, and the filename one an applicant will recognise on their own computer rather
  than a UUID.
- **The resolved map is never written back.** Assert the row's `personalisation` is unchanged after a successful
  send: this is the invariant the design rests on and it would break silently.
- A document that could not be read is `TEMPORARY`, and a personalisation that names no document id is `TECHNICAL`
  — neither is ever `PERMANENT` (decision 7 and its amendment). A document over 2 MB fails **before** `sendEmail`
  with a message naming it and its size (decision 8).
- Tests, **container-free** with a stubbed store and `StubNotify`: a send resolves a multi-document set; the stored
  row survives unchanged; an unreadable document yields a verdict `retryable()` admits; an oversized one fails with
  a useful message; and `confirm_email_before_download` and the retention period reach the client as configured.
- [x] documents resolve to uploads at drain time and are never persisted, the frozen row survives a send
      unchanged, an unreadable document is retried and an oversized one fails terminally, both with useful
      messages, and `./gradlew build` green

      **Done 2026-09-25 by [notify-4b](completed/notify-4b-generate-the-deed.md) Task 4, not by this plan**, and amended
      here in its Task 5 so nobody builds the seam twice. 4b's Task 4 needed a document reference to become a
      `prepareUpload` at drain time and was told not to wait for this plan; after the Notify discovery that the
      five static forms are attached to the *template* rather than supplied by api, the seam was a handful of
      lines rather than a subsystem.

      It is `notify/DocumentUploads` plus the sealed `ResolvedDocuments`, called from `NotifyEmailSender`
      immediately before `sendEmail`. **Decisions 3, 4, 7 and 8 are all implemented and asserted**: it resolves
      `EmailTemplate.documentKeys()` and never an arbitrary personalisation value, through
      `DocumentService.downloadDocument`, which is case-scoped — so a stored id cannot fetch another applicant's
      document; the frozen row survives a send unchanged; `confirm_email_before_download` is always true; a
      document that could not be read is `TEMPORARY` and one this service never froze an id for is `TECHNICAL`,
      neither of them `PERMANENT` (decision 7 as amended — it shipped saying `TECHNICAL` for both, which made the
      row terminal on its first attempt and the case unrecoverable); and an oversized one is refused **before**
      `sendEmail` with a sentence naming the document and the limit.

      **One thing this plan did not anticipate: the retention period is configuration with no default, and it is
      part of being provisioned.** `notify.document-retention-weeks`, and `NotifyProperties.isProvisioned` now
      asks **three** questions rather than two — a template carrying a document is unprovisioned without a
      period, exactly as a reply-inviting one is without a reply-to. Not positive means unconfigured, because a
      chart setting `0` would otherwise send an applicant a link to nothing. See 4b's flag 7 for the one claim
      about it that could not be verified from this devcontainer.

      **Tasks 2, 3 and 4 of this plan are untouched.**

## Flags

1. **AAT has no Notify key**, so every email AAT offers fails at the drain. Blocked on `azure-access#8111`
   (Steve into the `DTS Deed Poll` group, so the vault secret can be written).
2. **`DOCUMENT_STORE_ROOT` is local pod disk**, which is lost on restart and not shared between replicas. The
   deed is written through `DocumentStore` at send time and read back at drain time, so in AAT a restart between
   the two loses it. The read then retries as `TEMPORARY` until it lands on `Failed`, still holding V20's slot.
   **A deployment blocker for ① and ②**, and the subject of its own plan (the draft ADR 0005 in
   `deed-poll-documentation` is the starting point).
3. **Which forms a deed of relinquishment needs is unknown**, and so is whether it needs a generated deed.
   Decision 4 waits on it.
4. **admin's compose page is empty for a slotless template** (notify-4b flag 6). ① and ② have no slots, so the
   Email tab's compose step shows a heading, a hint about "the Master's direction" that has nothing to do with
   these emails, and a Continue button. It works, but looks broken. admin's to fix: skip to the mandatory check
   page when there are no slots, or state what will be sent.
