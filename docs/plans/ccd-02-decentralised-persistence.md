# Plan 02: decentralised CCD — the case pointer, the persistence contract, and the case type

## Why this plan exists, and why it is CCD rather than something smaller

**The driver is documents, not CCD.** `deed-poll-api` already serves documents end to end — `POST
/caseworker/cases/{id}/documents`, `GET …/documents/{documentId}/file`, `GET /caseworker/document-types`, the
whole `domain/documents/**` package and the `deedpoll_supportingdocument` table. What it does **not** have is
real storage: `DocumentStore` has exactly one implementation, `LocalFilesystemDocumentStore`, which its own
javadoc says "must not reach a deployed environment" because pod disks are ephemeral and replicas share
nothing.

Real storage is CDAM, and **CDAM requires a real CCD case.** That is not a preference, it is a code path:

- **Upload validates almost nothing.** `POST /cases/documents` takes `caseTypeId`/`jurisdictionId`/
  `classification`, and `DocumentManagementServiceImpl.validateCaseTypeId()` checks them only against CDAM's
  own classpath-bound `service_config.json` — never against ccd-definition-store or ccd-data-store.
- **Download calls back into CCD.** Every read runs `checkUserPermission()` →
  `CaseDataStoreClientImpl.getCaseDocumentMetadata()`, a real HTTP `GET {dataStore}/cases/{caseId}/documents/
  {documentId}`. A case CCD does not know produces `CaseNotFoundException`.

So **uploads would succeed and every download would 404.** That asymmetry is the single most important fact in
this plan: it means CDAM cannot be smoke-tested by uploading, and it is why CCD comes first.

**An Azure Blob store behind the same interface was considered and rejected on assurance grounds.** CDAM does
no file validation at all; **dm-store** is the only application-layer gate (extension + Tika MIME allow-lists),
and **Palo Alto AV sits upstream of the dm-store ingress at infrastructure level** — rejected files never reach
the blob (`apps/ccd/docs/explanation/document-extension-validation.md`). A plain storage account inherits
none of that. Staff uploading unscanned evidence into HMCTS storage is a security question, not an
engineering preference. Steve's decision, 2026-09-17: **take the standard CFT pattern — CCD + CDAM + dm-store
+ platform AV — and accept that it is more work.**

This plan is **CCD only**. It ends with a case type that exists, answers CCD's persistence callbacks, and
carries a CCD case reference on every new case. **Plan 03 swaps `DocumentStore` to CDAM** and is the only
thing that touches documents.

## Decisions taken — implement these, do not revisit

1. **CCD becomes the front door for case creation, and this is the invasive part.** Verified in source:
   `CasePointerRepository.persistCasePointerAndInitId()` is called from exactly one place,
   `SubmitCaseTransaction.submitDecentralisedCase()`, reachable only from `POST /case-types/{caseTypeId}/cases`.
   `DelegatingCaseDetailsRepository.set()` **throws `UnsupportedOperationException`** for decentralised case
   types. There is no "register an existing case" API — I looked. So a case that CCD did not create has no
   pointer, and can never have a CDAM document.
   PCS works exactly this way: the frontend submits a CCD create event, CCD allocates the reference in
   `SubmitCaseTransaction.submitCase`, then calls PCS's handler, which writes its own row with the reference
   CCD handed it (`CreatePossessionClaim.submit()` → `PcsCaseService.createCase(caseReference, …)`).
2. **Every case gains a CCD reference alongside its existing identifiers, and none are removed.** `DeedPoll`
   keeps its `@GeneratedValue(UUID) String id` and its `displayReference` (`KBDP2026-10100`). A new nullable
   `caseReference` (`Long`) column joins them, exactly as `PcsCaseEntity` carries both. Nullable **on purpose**
   — pre-existing cases have none, and decision 5 depends on that being representable rather than a
   constraint violation.
3. **`DeedPollState` is the CCD state enum, not a parallel one — but its members are frozen.** It is the `S`
   type parameter of `CCDConfig<T, S, R>`, so one Java enum both drives our domain and declares CCD's states.
   Its eight values (`Received`, `ReadyForMaster`, `ReferredToMaster`, `Enroled`, `Returned`,
   `AwaitingFurtherDocs`, `AwaitingSignature`, `AwaitingEnrolment`) become the case type's states. **Do not
   create a second enum to "map" to** — that divergence is what the type parameter prevents.

   **Two hard constraints on that enum, both stated in its own javadoc — read it before touching it.** The
   member **names** are the values the `"DeedPollState"` Postgres enum stores, so a rename stops it round
   tripping; and the member **order** is the Dynamics 365 option-set integer sequence, which the Dataverse
   exports hold. So: **add annotations, never rename, never reorder, never insert in the middle.**
   PCS's equivalent (`apps/pcs/pcs-api/.../ccd/domain/State.java`) shows the shape — each member carries
   `@CCD(label = …, access = {…})`, which is additive and safe here. A human-readable CCD label is exactly
   what `@CCD(label = …)` is for, so there is no reason to touch a member name to make CCD read nicely.
4. **Our own REST surface stays, in full.** Decentralisation intercepts only the `/ccd-persistence/*`
   contract; it does not take over our API. The field-level query API with sorting and paging keeps working
   against our own Postgres. CCD's ES-based search replaces SQL search **only for CCD-routed queries** — which
   we do not yet have. `decentralisation.md` "Design boundaries" is the authority. **No task may remove or
   reroute an existing caseworker endpoint.**
5. **Pre-existing (Dynamics-ported) cases get NO pointer in this plan, and that is a stated limitation rather
   than an oversight.** There is no documented backfill: a pointer is created transactionally inside event
   submission, so retrofitting means synthesising a create event per historical case — which allocates a
   *new* reference, requires reconstructing the original event's data shape, and would need existing documents
   re-associated with CDAM afterwards. The docs are silent on it; `decentralise-a-service.md` is an onboarding
   guide, not a migration guide. **Consequence to write down and carry: cases created before this lands
   cannot have CDAM documents.** Options — do nothing, backfill everything, or backfill on demand — are for a
   later plan with the business, not a task here. `LocalFilesystemDocumentStore` continues to serve them in
   development.
6. **Staff-only, so no per-case AM role assignment.** Documents are internal HMCTS staff only (Steve,
   2026-09-17). Organisational (`STANDARD`) roles suffice; the per-case (`SPECIFIC`) grants PCS needs for
   claimants and defendants are **out of scope**, and so is `am-role-assignment` integration. The definition
   grants CRUD to caseworker access profiles and nothing else. No citizen access profile.
7. **`/citizen/**` stays empty and gains nothing here.** It exists so `deed-poll-web` has a namespace later.
   A citizen CCD surface is a different plan with a different security argument.
8. **The `/ccd-persistence/*` controllers are generated — do not hand-write them.** The SDK generates
   `ServicePersistenceController`. What we write is the `CaseView` bean and the `Submit` handlers it calls.
   A task that creates a `@RestController` under `/ccd-persistence` is wrong.

## Open questions — flagged, NOT answered here

- **Whether CCD's create-event flow can be driven server-side by this service** so that `POST
  /caseworker/cases` keeps working as the create entry point (calling CCD internally with a system user + S2S,
  then storing the returned reference). The API allows it — `POST /case-types/{caseTypeId}/cases` is plain
  REST — but **I found no service in the workspace doing this**, and it is explicitly best-effort rather than
  transactional: a crash between the CCD call and our commit leaves a reference with no row or a row with no
  reference. `ccd-case-migration-starter`'s `CoreCaseDataService` is the closest pattern and it submits events
  on *existing* cases, not creates. **Task 1 investigates and reports; it does not implement.** This decides
  whether our create endpoint survives unchanged or the frontends must move to CCD's create flow, and it is
  too big to settle by inference.
- **Whether a pointer alone satisfies CDAM's permission check**, or whether event history is also needed.
  Source composition suggests existence + role is enough — `CreatorGetCaseOperation` does a visibility check
  and no state check, and for a decentralised case the data comes live from our `CaseView`, not the pointer
  (whose `data` is always `{}`). But no written spec confirms it for the decentralised case. **Plan 03 proves
  it end to end**; this plan does not depend on the answer.
- **Global Search.** PCS sets `SearchCriteria` in its `CaseView`. Not needed for documents, so not built.
  Recorded so its absence reads as a decision.
- **Retain-and-dispose / `resolved_ttl` echoing.** `decentralisation.md` flags that decentralised services
  must echo CCD's `resolved_ttl` unchanged, and that this is Confluence-sourced with no source validator
  found. Unclear whether it bites us. Read the note before implementing `CaseView`.
- **The SDK is moving.** `decentralisation.md`: "the team expects to evolve these designs upon contact with
  reality." Also a known divergence: the generated controller returns `200` with errors in the body where the
  design says `201`/`422`. **Source wins over the doc**; do not "fix" the SDK to match the LLD.

## Constraints

- **Never edit a committed Flyway migration — and check the next free number, do not trust this plan's.**
  On disk today the highest is **V7** (`V7__backfill_referrals.sql`), so the next free number is V8. **But
  `referrals-api-2-claim-direction-close.md` has already claimed V8**, and the referrals plans are being run
  in parallel by someone else. So the migration this plan adds is **"the next free number", most likely V9** —
  the owning task must `ls src/main/resources/db/migration/` and pick the first unused number at the moment it
  runs. Two plans writing `V8__` is a Flyway checksum failure that surfaces on the next boot, not at compile
  time.
  Mixed-case quoted columns and `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` for enum columns —
  `globally_quoted_identifiers` is on.
- **No live calls to CCD, CDAM, IDAM or payments in any test.** WireMock only. No credentials exist here.
- `TESTCONTAINERS_RYUK_DISABLED=true` is required on this machine, and Testcontainers reaches containers over
  the Docker bridge rather than a published port (`ContainerDatabase`).
- **Expect a first-build artefact fetch.** `decentralised-runtime`, `ccd-runtime-indexing` and `ccd-sdk-bom`
  resolve from GitHub Packages/JitPack, and this devcontainer is behind a proxy that has blocked downloads
  before. If resolution fails, that is an environment problem to report — **not** a reason to vendor a jar or
  pin a different version.

### Task 1: Investigate how a case gets created, and REPORT — do not implement

**This task writes a finding, not code.** It settles the plan's largest open question: does `POST
/caseworker/cases` survive, or must creation move to CCD?

The facts already established, which you should verify rather than rediscover:

- `CasePointerRepository.persistCasePointerAndInitId()` has exactly one caller,
  `SubmitCaseTransaction.submitDecentralisedCase()`, reached only from `POST /case-types/{caseTypeId}/cases`.
- `DelegatingCaseDetailsRepository.set()` throws `UnsupportedOperationException` for decentralised types.
- PCS's frontend submits a CCD create event; CCD allocates the reference; PCS's handler stores it.
- Our `CaseworkerCaseController.create()` (line 69) writes our row directly and returns our UUID.

What to determine:

1. **Can this service call CCD's create-case API itself**, with a system-user IDAM token and an S2S token, so
   that `POST /caseworker/cases` keeps its contract and gains a CCD reference behind the scenes? Read
   `CaseController.java` in `ccd-data-store-api` for what the endpoint requires (start-event trigger token,
   event token), and `ccd-case-migration-starter`'s `CoreCaseDataService` for the S2S + system-user pattern.
2. **What breaks if we do.** The call is not in our transaction. Enumerate the failure modes and say which are
   tolerable: CCD pointer created then our commit fails; our commit succeeds then the CCD call fails; a
   duplicate submission.
3. **The alternative**, honestly costed: the frontends stop calling `POST /caseworker/cases` and submit a CCD
   create event instead, PCS-style. What does that cost `deed-poll-admin` and `deed-poll-web`?
4. **A recommendation**, with the reasoning, written into this plan as a new decision.

**Contingency, and it is the point of the task:** if neither option is clearly safe, **stop and report.** A
guess here is a rewrite of the create path in three repos. It is entirely acceptable for this task to
conclude "creation must move to CCD and that is a separate plan for the frontends" — that is a finding, not a
failure.

## How to know it worked, and what is still not proven

Green `./gradlew build` plus a generated definition means the *service side* is right. It does **not** prove
CCD can route to us — that needs the platform routing entry, and a real environment.

**What this plan deliberately does not deliver:**

- **No document goes to CDAM.** `DocumentStore` is untouched; `LocalFilesystemDocumentStore` is still the only
  implementation. That is plan 03.
- **No pre-existing case gets a pointer** (decision 5), so no ported case can have a CDAM document. This is
  the limitation most likely to surprise someone, and it needs a business conversation rather than a task.
- **Nothing is deployed.** The chart, the routing entry and the CDAM onboarding are external.

The first end-to-end proof is plan 03's, and the honest test there is a **download**, not an upload — because
an upload succeeds whether or not the case exists in CCD.
